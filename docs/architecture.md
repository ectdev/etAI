# How the parts fit together

The shape of the repository, the data model behind it, how access is decided, what
the tests cover, and the design decisions worth explaining.

## Project layout

```
apps/
  web/          Next.js app: pages, API routes, and the MCP HTTP transport
    lib/        auth configuration, session helpers, error types
  mcp-server/   MCP server over stdio, for clients that launch a subprocess
packages/
  core/         ingestion, retrieval and answer generation
  db/           database schema, migrations
  shared/       validation schemas and types used on both sides of the boundary
corpus/         the document collection that gets indexed
```

Everything the system can do with the documents lives in `packages/core`, and it
depends on neither Next.js nor HTTP. The chat page, the stdio MCP server and the
HTTP MCP route are three entry points into the same code rather than three
implementations of the same idea.

That package publishes four names: `searchChunks`, `answerQuestion`, `ingestCorpus` and
`indexStats`. It used to publish thirty, of which two were called from outside, because
every module's exports had been forwarded whether or not anything wanted them. The
measurement harness sits behind `@etai/core/eval`, since running a measurement is
something done to the system rather than something the system does. A test asserts the
list, so a name appears there because somebody chose to publish it.

## Data model

| Table                                        | Holds                                                                        |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| `user`, `session`, `account`, `verification` | Sign-in state, with the role kept on the user                                |
| `document`                                   | One row per file: where it came from, when it is from, whether it is current |
| `chunk`                                      | The text that gets embedded and searched, one row per piece                  |
| `ingestion_run`                              | One row per run: what triggered it, when it ended, how it went               |
| `ingestion_item`                             | One row per file per run, so a partial failure names the files it hit        |
| `search_query`                               | One row per question, including how much of it the collection covered        |

The split between the two corpus tables is what a document is against what gets
searched. Metadata that answers "is this current" belongs to the file, so it sits on
`document` and one lookup serves every chunk of it. Ranking can then compare a vector
against that metadata in a single query, which is the advantage of keeping both in one
database.

The keyword-search column lives on `chunk` and is generated by PostgreSQL from the
heading trail and the text, so it cannot fall out of step with what it came from. The
heading is included because the term someone searched for is often in a heading rather
than in the sentence below it.

## How access is decided

Two things guard a private page, and they are not redundant.

The middleware checks whether a session cookie exists and sends visitors without one
to the sign-in page. That is all it does. It runs on every matched request, so
querying the database there would add a query to every page load, and it cannot read
a role without one. A forged cookie gets past it.

The page or the handler then reads the real session and checks the role. This is the
check that decides anything. It is repeated in every handler rather than being
inferred from the path, because a middleware matcher is a pattern, and a route added
later that does not match the pattern would otherwise be open.

Two smaller choices in the same area. The role is stored on the user rather than
looked up separately, so a session read already carries what a permission check
needs. And the role field is not writable through the auth endpoints, which is what
stops a crafted update request from handing someone the admin role.

## Tests

```bash
pnpm test           # unit and integration, needs the database running

pnpm dev            # in one terminal
pnpm verify:http    # in another
```

The suite is narrow on purpose. It covers the places where a mistake would be silent
rather than trying to reach a coverage number.

Three examples of what that means. The database tests read the query plan for a
cosine-ordered search, because a vector index built for the wrong distance function
returns correct results and is never used, so checking that the index exists
proves nothing. The sign-in tests create a user, sign in, and read the role back out of
the session, because the auth tables were written by hand and comparing column names
turned out to measure nothing at all. And the error tests assert that an unexpected
failure does not put its message in the response body, since a stray error can carry a
connection string.

`pnpm verify:http` covers what unit tests cannot reach: what a browser gets when it
asks for a page it is not allowed to see. It checks that a signed-out visitor is
redirected and told where to come back to, that a forged cookie is not enough, that the
ordinary user is turned away from the dashboard while the admin is not, that the
session cookie is `HttpOnly` and `SameSite`, and that repeated sign-in attempts get
throttled while session reads keep working.

## Design decisions

### pnpm workspaces without a build orchestrator

Turborepo and Nx both solve a real problem, which is task orchestration and
caching across a large number of packages. This project has five, and their build
order is a straight line. Adding a caching layer would mean another config file
and another concept to explain, in exchange for saving a few seconds on a build
that already takes about one.

TypeScript project references handle what actually matters here: the packages know
about each other, `tsc --build` rebuilds only what changed, and a type shared
between the server and the browser is the same type rather than two that happen to
agree.

### A chunker that leaves these documents whole

Documents are chunked on their headings, with a token budget and two fallbacks for
sections that overrun it. On this collection every document comes out as a single
chunk, all 131 of them, because the largest file is 572 tokens against a budget
of 800.

Writing a chunker that then does nothing visible sounds like wasted work, and the
alternative is worse. Ingestion has to work on a folder of markdown files rather than on
this folder of markdown files, and a pipeline that embeds whole files works here and
fails on the first document longer than the model's input limit. The behaviour on this
collection is an outcome of the budget, not an assumption baked into the code.

It also happens to be the better outcome here. A citation points at a document a person
can open and read, rather than at a fragment they have to place. See [Chunking](retrieval.md#chunking)
for how the splitting works and what it does to the 61 templated deployment reports.

### The vector database is pgvector, inside PostgreSQL

This project does use a vector database. pgvector is one, it just runs as an extension
inside PostgreSQL rather than as a service of its own. Vectors are stored in a `vector`
column, searched with a cosine distance operator, and indexed with HNSW.

Choosing it over Qdrant, Pinecone or Weaviate was the decision. Any of those would have
been a second service to run, a second connection to configure, and a second thing to
install before the project starts. With this many documents it would buy nothing
measurable in return.

Keeping the vectors in the same PostgreSQL instance as the application data has a
real advantage beyond simplicity: ranking can compare a vector against document
metadata in one query, which is what this collection needs. Knowing that
a document is out of date is often more useful than knowing that it is similar.

### HNSW with an operator class that matches the query

The vector index is not here for speed today. At 131 rows the planner reads the whole
table in about 5 ms and that is the right choice, so the index is not used at this size.

It is here for the size after this one, and that only works if the query is a shape the
index can serve. Two things have to line up. The operator class has to match the
distance function, because an index built for cosine distance is invisible to a query
asking for anything else, so the index names `vector_cosine_ops` explicitly. And the
ordering has to be the whole query: HNSW answers `ORDER BY embedding <=> $1 LIMIT n` by
walking a graph, which it cannot do if the rows have to be joined and filtered first.

The second one was wrong here and the plan is what said so. The vector query joined
`document` to skip documents that had been removed from disk, and with that join the
plan was a sequential scan and a top-N sort even with sequential scans turned off. The
index was unreachable rather than merely unused, which is the version of this that never
shows up until the table is large enough for it to matter.

The join was also doing nothing. A document removed from disk keeps its row, for the
ingestion history, and loses its chunks, so no chunk sits behind a deleted document for
the filter to catch. Removing it makes the plan an index scan when sequential scans are
disabled, which is the check that the shape is right; at this row count the planner
still picks the scan, which is the check that it is being sensible. The rule the removal
depends on is asserted in `persist.test.ts` rather than assumed.

The type-filtered version keeps its join and does not want the index. With a selective
filter, finding the few matching rows and sorting them beats walking a graph and
throwing most of the results away, which is what its plan shows.

HNSW rather than IVFFlat because IVFFlat wants rebuilding as rows change, and this
collection is meant to be re-indexed whenever the files do.

### 1536 dimensions rather than the default 3072

Gemini Embedding 2 returns 3072 numbers per document by default. pgvector stores
that happily but cannot build an HNSW index above 2000 dimensions, so the index
would have to be dropped and every search would fall back to scanning the whole
table.

Asking the model for 1536 dimensions solves this. The model is trained so that a
shortened vector keeps its meaning, and it still comes back at unit length at
this size, so cosine distance works without any extra normalisation step.

## Decisions in the interface

**Retrieval scores and timings are shown to administrators only.** A cosine distance
does not help somebody decide which document to open, and printing one beside every
source turns a search tool into a debug view. The same numbers are what somebody
inspecting the system needs, so an admin sees the distance, the rank, the retrieval and
generation times and the model name, and a regular user sees the document, its type, its
date and whether it is out of date. The cut is made on the server: a field sent to the
browser and hidden with CSS has still been disclosed.

The coverage badge stays visible to everyone. Whether the collection covered a question
is the answer's own status rather than diagnostic detail, and it is the thing a reader
most needs to know about what they are reading.

**Citations are marked in the text, and the marks are checked rather than trusted.** The
model is asked to mark each claim with the number of the document it came from, and each
mark becomes a button that opens that document at the passage it quoted. A claim resting
on two documents gets a button for each. None of it is taken on trust: a mark pointing
outside the documents that were actually retrieved is removed before the answer is sent,
because a reference nobody can follow is worse on every surface than no reference, and an
MCP client receives the same text without an interface to soften it. A mark pointing at a
retrieved document the answer did not cite is left where it is, counted, and rendered as
plain text rather than as a button that opens nothing. What each check does and
deliberately does not do is in [Answering](retrieval.md#answering).

**The integration tests look for a wider class of failure than the code knows about.**
They match anything bracket-shaped with a digit in it, not the marker syntax the
application implements. That is deliberate. The combined form `[1, 7]` went unnoticed
through a parser, a validation gate and nine passing tests because every one of them
shared the same limited idea of what a marker is, and a test that shares production's
assumptions cannot find the failures those assumptions cause. It is the reason the
integration tests sit in the gaps between components rather than inside them.
